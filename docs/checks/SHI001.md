# SHI001: anyone can write an account that has an owner

An instruction can write an account whose data names an owner (a `Pubkey` field such as
`cabal`, `authority` or `admin`), and nothing ties that stored key to a signer of the
instruction.

Anchor checks that a `Signer` signed. It does not check that the signer is the one the
account names: that is `has_one`, and it is opt-in. Leave it out and the program still
compiles, deploys and passes a happy-path test, while anyone who signs anything can
withdraw, close or rewrite the account.

typeshi refuses it.

## Example

```shi,fail
gm!("7PxhmDuhhe394QJgKyW1P7Ce4dPCfFPN2yKq4KCCj7Vj");

stealth_launch vault {
    frame Vault {
        cabal: Pubkey,
        balance: u64,
    }

    cap_table Withdraw {
        #[account(mut)]
        vault: Account<Vault>,
        cabal,
    }

    lock_in fn withdraw(ctx, amount: u64) -> W {
        mark_to_market!(vault.balance = per_my_last_email!(vault.balance) - amount);
        were_so_back!()
    }
}
```

`cabal` signs, but `vault.cabal` is never compared with it. Any wallet can pass itself
as `cabal`.

## Fix

Tie the stored owner to the signer with `has_one`:

```shi,pass
gm!("7PxhmDuhhe394QJgKyW1P7Ce4dPCfFPN2yKq4KCCj7Vj");

stealth_launch vault {
    frame Vault {
        cabal: Pubkey,
        balance: u64,
    }

    cap_table Withdraw {
        #[account(mut, has_one = cabal)]
        vault: Account<Vault>,
        cabal,
    }

    lock_in fn withdraw(ctx, amount: u64) -> W {
        mark_to_market!(vault.balance = per_my_last_email!(vault.balance) - amount);
        were_so_back!()
    }
}
```

A `constraint` that names the owner, or `seeds` built from the signer's key, count too.

When anyone really may write the account (a deposit, a public counter), say so with
`public`. typeshi drops the word from the Anchor it writes; it is there so the next reader,
and the compiler, know it is on purpose:

```shi,pass
gm!("7PxhmDuhhe394QJgKyW1P7Ce4dPCfFPN2yKq4KCCj7Vj");

stealth_launch vault {
    frame Vault {
        cabal: Pubkey,
        balance: u64,
    }

    cap_table Deposit {
        #[account(mut, public)]
        vault: Account<Vault>,
        ser,
    }

    lock_in fn deposit(ctx, amount: u64) -> W {
        mark_to_market!(vault.balance = per_my_last_email!(vault.balance) + amount);
        were_so_back!()
    }
}
```

## What it has cost

- **Cashio, 2022-03-23: $52.8M.** The collateral's accounts were never tied to each other,
  so a chain of fake accounts passed every check and minted unbacked stablecoins.
  [CertiK's analysis](https://www.certik.com/blog/cashio-app-incident-analysis).
- **Raydium's legacy AMM V3 program, 2026-06-10: about $1.34M.** A pool's LP mint was never
  checked against the pool, so a fake mint drained it. Reported by a security researcher,
  [@0xINFRA](https://x.com/0xINFRA/status/2064738005697384476); no official post-mortem found.

Audit firms see the same thing at scale: in Sec3's 2025 ecosystem review, access control
was 20.7% of high and critical findings in Solana programs
([report](https://sec3.dev/report)).

## What it doesn't catch

typeshi follows `has_one`, `constraint`, `seeds` and `address` back to a signer, through
other accounts (`bag.desk == desk`, `desk.cabal == cabal`). It checks that a tie exists, not
that the `constraint` you wrote is the right one. And no compiler stops a stolen key: since
2024 most money lost on Solana went that way.
